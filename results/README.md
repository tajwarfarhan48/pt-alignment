# Cross-backend comparison: CPU vs GPU (CUDA) vs Cerebras CS-3

Two separate deliverables live here, both comparing the same three backends
on the same data:

**See `HARDWARE.md` for what node/CPU/GPU each result actually ran on, and
whether that hardware was shared with other users' jobs during the run** --
the two independent CPU sweeps disagree by ~13-15% across every point, which
is exactly the kind of gap a hardware note should explain rather than leave
as unexplained variance.

## 1. Correctness comparison (10-sequence MSA)

All three backends run the identical pipeline (all-pairs global alignment ->
UPGMA guide tree -> progressive profile-profile merge) on the identical
input: `test/plasmid_sample.fasta` (10 real NCBI plasmid sequences, one per
species -- E. coli, K. pneumoniae, S. enterica, S. aureus, E. faecium,
A. baumannii, B. cereus, P. aeruginosa, C. perfringens, N. gonorrhoeae -- all
exactly 1000bp), with the same default `ScoreParams` (match=2, mismatch=-1,
gap=2). `guide_tree.cpp` and `progressive.cpp` are the *same unchanged
source* across all three backends -- only the all-pairs scoring stage
differs by hardware. So `score_matrix.txt` is the number to diff first; if
that matches exactly, `guide_tree.newick` and `final_msa.fasta` are
guaranteed to match too (same deterministic code fed the same numbers).

Each backend's directory should end up with:
- `score_matrix.txt` -- n x n whitespace-separated ints (0 diagonal)
- `guide_tree.newick` -- UPGMA tree, Newick format
- `final_msa.fasta` -- aligned FASTA, one record per input sequence, original IDs
- `full_output.txt` -- full console output (score matrix + tree + MSA + timing)

**cpu/ -- done.** Generated by `cs3/milestone2_allpairs/cli/cs3_msa_cli --fasta test/plasmid_sample.fasta --cpu-reference --out final_msa.fasta`,
which calls `align_cpu()` directly (`src/cpu_reference.cpp`, no GPU/CS-3
involved) for every pair, then the same `guide_tree.cpp` / `progressive.cpp`
used by the other two backends.

**gpu/ -- to be run on ACES.** `./bin/msa_align --fasta test/plasmid_sample.fasta --msa --out results/gpu/final_msa.fasta | tee results/gpu/full_output.txt`,
then extract `score_matrix.txt`/`guide_tree.newick` from `full_output.txt`
the same way `results/cpu/` was built (see git history for the exact `sed`/`awk`).

**cerebras/ -- pending real-hardware queue.** Generated by
`cs3/milestone2_allpairs/run_allpairs.py` (all-pairs, writes `scores.txt`)
piped into `cs3_msa_cli --scores scores.txt --out final_msa.fasta`.

## 2. Runtime / memory / I/O-share benchmark sweep

A separate, larger comparison: for n = 10, 20, 40, 80, 160, 320, 640
sequences (doubling), all-pairs alignment wall time, peak memory, and % of
wall time spent on I/O (host<->device transfer) vs. actual compute, on all
three backends. Uses a different, larger dataset --
`test/sweep_dataset.fasta` (2000 real plasmid sequences, all 1000bp) --
since 10 sequences isn't enough to sweep up to n=640.

All three write the same CSV schema: `n,pairs,wall_ms,kernel_ms,io_ms,io_pct,mem_used_mb`.
- **CPU**: `results/sweep_cpu.cpp` -> `results/sweep_cpu.csv`. No device
  transfer step exists for CPU, so `io_ms`/`io_pct` are always 0 by
  definition (a real structural difference between backends, not a missing
  measurement). `mem_used_mb` is peak RSS (`getrusage`), and comes back
  essentially flat across n -- expected, since align_cpu() processes one
  pair's DP matrix at a time and doesn't accumulate memory across pairs.
- **GPU**: `--sweep` flag added to `src/main.cu` (`run_sweep`), writes
  `results/gpu/sweep_gpu.csv`. `kernel_ms` is pure on-device time (already
  tracked per-call via `AlignResult::kernel_ms`); `mem_used_mb` via
  `cudaMemGetInfo` before/after each sweep point -- note `gpu_align.cu`'s
  `align_gpu_pt` allocates and frees its device buffers within each call, so
  this reads near-zero net delta by design (no persistent allocation across
  pairs), which is itself a legitimate finding, not a bug.
- **Cerebras CS-3**: `cs3/milestone2_allpairs/run_sweep.py`, writes
  `sweep_cerebras.csv`. `kernel_ms` is the time inside `launch('compute')`
  only; `io_ms` is time inside the `memcpy_h2d`/`memcpy_d2h` calls.
  `mem_used_mb` is *not* runtime-queried (no memory-query API found on the
  SdkRuntime client used here) -- it's computed analytically from the
  kernel's fixed per-PE array sizes, which don't change across sweep
  points since every pair reuses the same PE memory sequentially. One
  compile serves the *entire* sweep: every sequence in the dataset is the
  same 1000bp, so the kernel shape (m=n=1000 PEs) never changes -- sweeping
  n only changes how many pairs run through that one fixed-shape kernel.

**Substitution matrix / sequence transfer strategy (CS-3), since it's
easy to lose in the CSVs**: no substitution matrix is used at all --
scoring is uniform match/mismatch/gap scalars, compile-time constants
(this project's DNA-alignment convention throughout, ACGT only). Sequence
A: one character per PE, uploaded as one `memcpy_h2d` (one distinct
`int32` per PE, row-major onto the PE line). Sequence B: broadcast --
the *same* full array copied to *every* PE's local memory
(`np.tile` + one `memcpy_h2d`), so each PE walks all of B locally with
zero fabric traffic during compute.

**View the rendered charts**: `results/benchmark_report.html` (regenerate
via the script in the session scratchpad, or by hand -- reads whatever CSVs
exist on disk, shows "pending" badges for series not yet populated).

**Literal 16k-72k sequences was not run**: all-pairs is O(n^2) pairs; at
n=16,000 that's ~128M pairs, at n=72,000 ~2.6B pairs -- multiple orders of
magnitude beyond what fits in this task's time budget on any of the three
backends (measured CPU rate alone extrapolates to ~318 days at n=72,000).
The sweep above measures the real O(n^2) trend on a feasible range instead.
