1. Runtime vs # of sequences

Wall time (log y-axis — pair count grows O(n²), so linear would flatten the small-n points to invisibility).

Why CS-3 has two series: "sequential" is one PE per pair, one launch per pair — simple, but ~99% of wall time is per-pair network round-trip overhead (see section 3). "batched" tiles up to 750 pairs across fabric columns per launch, relaying sequence B PE-to-PE instead of replicating it from the host, which amortizes that round-trip cost. Both series are now real, measured, real-hardware data at every matching n (10–160) — batched is 28x faster at n=10, rising to 470x by n=160 as the per-launch overhead gets spread over more pairs. Sequential was not run past n=160: at its measured rate, n=320/640 would take ~2.2h/~8.7h for a redundant data point once the fix was already known, so batched continues on alone to n=320 (16.98s) and n=640 (66.70s) — a ~500x-and-climbing improvement over what sequential's rate would project to at the same n.

2. Memory usage vs # of sequences

Peak working-set memory. Structurally flat is the expected/correct shape here, not a bug: every backend processes pairs sequentially, reusing one fixed-size working set (the DP matrix for one pair, or the CS-3 kernel's static per-PE arrays) rather than accumulating state across pairs. CS-3 (batched)'s footprint is flat too, but ~750x larger than sequential's — same per-PE footprint, ~750x more PEs active per launch (computed from kernel array sizes, not runtime-queried, same as the sequential series).

Sequence/substitution-matrix transfer strategy (CS-3): no substitution matrix is used — scoring is uniform match/mismatch/gap scalars baked in at compile time (DNA alignment convention this whole project uses; ACGT only). Sequences: one PE per character of sequence A (one distinct int32 per PE via a single memcpy_h2d, row-major onto the PE line); sequence B is broadcast identically to every PE's local memory (np.tile + one memcpy_h2d), so each PE walks all of B locally with zero fabric traffic during compute. One compile serves the entire sweep, since every sequence in the dataset is the same 1000bp — sweeping n only changes how many pairs run through the same fixed-shape kernel. GPU: per-pair H2D/D2H of the two sequences and the resulting H/TB matrices; kernel_ms is pure on-device compute time, tracked per-call in this codebase already.

4. Device utilization

A metric that only exists for one of the three backends — reported as-is rather than papered over.

GPU: real, measured, via nvidia-smi sampled every 5s throughout the ACES sweep run — 68.3% average utilization (min 0% at startup, max 71%), on the single H100 allocated (exclusively) to this job; see results/gpu/gpu_utilization.csv.

CS-3: no equivalent metric is obtainable. Checked thoroughly, not assumed absent — neither csctl nor the SDK's own instrumentation tools (InstrTrace, WaveletTrace) expose PE-activity data for real hardware in this SDK version (both require a simulator log file as input). What is knowable: wafer allocation is all-or-nothing (100%, confirmed empirically — the scheduler never runs two execute jobs concurrently), and this kernel's own PE-grid occupancy of that allocation is analytically ~0.11% (1,000 of 893,064 addressable PEs) for the sequential single-pair design above — a batched redesign explored separately (see results/README.md section 3) raised that to ~85% PE occupancy and cut all-pairs wall time by roughly 500x, without ever producing a utilization percentage the way nvidia-smi does, since the underlying telemetry simply isn't exposed. Full detail: results/HARDWARE.md.

CPU: not applicable in the same sense (no device to under/over-utilize) — the sweep is deliberately single-threaded, matching the GPU/CS-3 legs' "one pairwise alignment's worth of parallelism per launch" framing rather than exploiting all cores, so a core-utilization number here would measure the sweep script's threading choice, not the hardware.
